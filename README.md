# Hive Inspect - Template Importer

A template migration workflow for inspection companies moving from Spectora to
Hive Inspect: import a Spectora "Export HTML Text" spreadsheet, edit the
result, duplicate templates independently, and keep it all in a real
database.

## The customer problem

An inspection company has spent years tuning their Spectora template. They
will not retype it. This app takes their actual Spectora export, parses it
into a structured, editable template, and lets an inspector work with it
without losing anything from the source - including flagging, visibly,
anything it could not map.

## Architecture

```
Upload (.xls/.xlsx)
  -> validate (type, size, workbook structure)
  -> parse workbook into a row grid            (src/lib/importer/workbook.ts)
  -> map rows -> sections/items/comments        (src/lib/importer/mapRows.ts)
     - HTML entity decoding for plain-text fields
     - HTML sanitization (allowlist) for comment text
     - warnings collected, never thrown away silently
  -> preview (stats + warnings) shown to the user, nothing written yet
  -> on confirm: one DB transaction creates template/sections/items/comments
     + an `imports` row recording warnings and counts (src/db/repo.ts)
  -> editor: section/item/comment name + comment text are editable,
     each edit re-sanitized and saved via a Server Action
  -> duplicate: deep-copies the whole hierarchy with new IDs in one transaction
```

The importer (`src/lib/importer/`) is pure and has no dependency on the
database or Next.js - it is fully unit-testable and works on any workbook
that uses the same Spectora column headers, not just the committed fixture.

## Technology stack

- **Next.js 16 (App Router) + TypeScript + React 19** - a single deployable
  app, Server Actions instead of a separate REST layer, easy to run on Vercel.
- **PostgreSQL via Drizzle ORM** (`postgres` driver) - Supabase-hosted in
  production, any Postgres works locally. Migrations are plain SQL files
  generated by `drizzle-kit`, checked into `drizzle/`.
- **exceljs** to parse the uploaded workbook (chosen over SheetJS/`xlsx`,
  which has open, unpatched ReDoS/prototype-pollution advisories - see
  DECISIONS.md).
- **sanitize-html** to allowlist-sanitize comment HTML, both on import and
  on every edit.
- **Vitest** for the parser unit tests and DB integration tests.
- **Tailwind CSS v4** for styling.

## Local setup

### 1. Install dependencies

```bash
npm install
```

### 2. Database

Any Postgres instance works. Two options:

**Option A - local Postgres** (fastest for development):

```bash
createdb hive_inspect_dev
cp .env.example .env.local
# edit .env.local -> DATABASE_URL="postgresql://<you>@localhost:5432/hive_inspect_dev"
```

**Option B - Supabase** (what the deployed app uses):

1. Create a free project at supabase.com.
2. Project Settings -> Database -> Connection string -> URI. Use the
   **direct** connection (port 5432) for migrations/local dev; use the
   **transaction pooler** connection (port 6543) for Vercel.
3. `cp .env.example .env.local` and paste the connection string into
   `DATABASE_URL`.

Then run the migration:

```bash
npm run db:migrate
```

### 3. Seed the database

Seeds from the committed Spectora export (`InterNACHI Residential
-2026-09-19.xls`) so the app opens with a real, already-imported template
instead of an empty state. Safe to re-run - it no-ops if any template
already exists.

```bash
npm run seed
```

### 4. Run the app

```bash
npm run dev
```

Open http://localhost:3000 - you should see the seeded InterNACHI
Residential template. Use "Import Spectora template" in the header to import
another export.

## Environment variables

| Variable | Required | Notes |
|---|---|---|
| `DATABASE_URL` | Yes | Postgres connection string. Never exposed to the browser - only read in server-side code (`src/db/client.ts`, Server Actions, the seed script). |

No other secrets are used. There is no service-role key, no auth provider,
and no third-party API key in this project.

## Testing

```bash
npm test        # parser unit tests - deterministic, no database required
npm run test:db # DB integration tests - persistence, editing, duplication,
                 # independence, transactional rollback. Requires DATABASE_URL.
```

`npm test` is safe to run with zero setup (CI, a fresh clone, a reviewer who
hasn't touched the database yet) - it skips the DB-dependent suite rather
than failing it. See NOTES.md for what each test file actually covers.

## Build

```bash
npm run build
npm start
```

## Deploy

The app is a standard Next.js app - deploy it to Vercel like any other:

```bash
vercel
```

1. Set `DATABASE_URL` in the Vercel project's environment variables, using
   the Supabase **transaction pooler** connection string (port 6543) so
   serverless functions don't exhaust the direct-connection limit.
2. Run `npm run db:migrate` once against that same database (from your
   machine, using the direct connection) before or after the first deploy.
3. Run `npm run seed` once (same way) so the live app opens with the
   InterNACHI template already imported, per the assignment's requirement.

Live URL: https://hive-inspect-template-importer-ten.vercel.app

## Importing a Spectora template

1. In Spectora, open a template (e.g. InterNACHI Residential) and choose
   **Export to spreadsheet -> Export HTML Text**. Use that file, not the
   plain-text export.
2. In this app, go to **Import Spectora template**, choose the file, and
   click **Preview import**. You'll see section/item/comment counts and any
   warnings before anything is written to the database.
3. Click **Import template** to commit it. You're redirected to the new
   template's editor.

## Supported input format

A single-sheet `.xls`/`.xlsx` workbook (Spectora's export is actually an
OOXML/`.xlsx` file with a header row containing at least `Section Name`,
`Item Name`, and `Comment Name`. The importer also reads (when present)
`Comment Text`, `Comment Type`, `Category`, `Multiple Choice Options`, `Unit
Type Options`, `Recommendation`, `Order (w/i item)`, `Answer Type`, and
`Default Value`. Column order does not matter, and unrecognized extra
columns produce a warning rather than a failure. See NOTES.md for the full
breakdown of what was actually found in the committed export and how each
field is handled.

## Sample export

`InterNACHI Residential -2026-09-19.xls` (committed at the repo root) -

template, via Export to spreadsheet -> Export HTML Text.

## Known limitations

See NOTES.md for the full list. Briefly: the editor edits section/item/
comment names and comment text (per the assignment's baseline); other
per-comment fields (answer type, multiple-choice options, severity,
recommendation) are imported, preserved, and shown, but not yet editable.
Comment text is edited as sanitized HTML in a plain textarea with a live
preview, not a WYSIWYG editor.
